# Verification — id-tokens (2026-08-22)

Change: item IDs become random six-character tokens, minted when the item is
written, instead of sequential numbers assigned at merge. Branched from `main`
at `7e9009b`. Plan: `docs/plans/2026-08-22-id-tokens.md`.

Not a defect fix. The defect it removes is operational: sequential numbers are
allocated against a moving base branch, so two changes finalized against the
same base mint the same number and whoever merges second re-finalizes. The user
runs agents in parallel and expects multi-person GitHub collaboration, where
that is a rewrite of every `verifies:` annotation at merge time. A token
allocated against nothing cannot collide by construction.

Both ID forms are accepted, permanently. `GR_ID_BODY` is
`(<token>|[0-9][0-9][0-9]+)`, so a project that predates this change keeps its
numbers and nothing converts an existing SRS. The corpus measurement below is
that guarantee under test.

### The one corpus difference

```
MALFORMED-ID docs/problems/2026-08-19-duplicate-pr-ids.md:179:**PR-NNN**: a probe item …
```

Exit 0 on `main`, exit 1 here. The line is illustrative text at column one
inside a fenced code block — written as `NNN` precisely so the old
digits-only patterns would not match it. It is a true positive by this
toolkit's own rules: no gate here parses markdown fences, so a *real*
definition inside one is a definition to `DUPLICATE-ID`, and a malformed one
inside one is malformed to this gate. Two tests pin both halves of that
("a definition form inside a fenced code block is still judged", "indenting
that same form is what makes it prose"), and the cost is stated in the four
ledger templates and in `ratchet`'s upgrade note rather than left to be
discovered.

The remedy for the corpus is two spaces of indentation. It is not a change
this branch makes: `sightings-app` is not touched from here.

### Blocking

**B1 — `DUPLICATE-ID` swallowed a failing scan and reported a clean tree.**
`check-ids.sh`'s duplicate scan suppressed stderr and checked no status, three
lines below a comment condemning exactly that, and it was a pipeline, so `$?`
was `uniq`'s in any case. Demonstrated by injecting a `git grep` failure: the
draft and MALFORMED scans died with exit 2, this one exited **0 over a tree
holding two definitions of the same ID**. The same shape was in
`check-trace.sh`'s reference harvest — a line this change wrote — where an
injected failure made `DANGLING-REF` vanish and the run exit 0.

This is the project's own thesis failing, and this change made it worse in one
specific way: deleting the duplicate-vs-base gate left the in-tree scan as the
only gate against a duplicate ID. Both sites now capture, check status, and
reduce afterwards. Pinned by two fault-injection tests that put a failing `git`
on `PATH`, and by mutation rows `M47` and `M48`.

**B2 — a shipped skill carried a live, misplaced item definition.** This change
rewrote `skills/resolve-problem/SKILL.md` to show a minted ID, and wrote
`**PR-p9r5wx**:` at column one. On `main` that line read
`**PR-DRAFT-<branch>-<n>**:`, which matched nothing. A project that vendors the
skills in-repo — routine under `.claude/skills/` — gets `MISPLACED-ITEM
PR-p9r5wx` and `PR 1` in its `checked:` line. The change broke the rule it
introduced, in the artifact that teaches the rule. Indented and given the
placeholder body, like the four ledger templates.

## Two defects found during verification, both fixed here

Neither was found by the suite or by the mutation table. Both were found by
running the tooling over the 1178-file corpus and by probing the new ID shape
by hand — which is the method's standing limit restated: mutation can only
redden a gate that already has a test.

**1. `MALFORMED-ID` reported the lines that mention a bad form, not the lines
that open one.** The first implementation harvested the forms with `git grep
-o` and then searched for each one literally to find its location. On the
corpus that turned one violation into ten report lines, nine of them ordinary
prose quoting the form. Fixed by composing both patterns in a single
`git grep --and --not`, which decides per line and needs no second pass and no
path framing. Pinned by "MALFORMED-ID reports the lines that open one, not the
lines that mention one".

**2. A reference one character too long was credited to the item it truncates
to.** `verifies: REQ-a3k9z2x` is not a reference to anything — a token is
exactly six characters — but the harvest matched its first six and reported
`REQ-a3k9z2`, so a real requirement went green on a test that verifies
nothing. This is a false green the scheme introduces: sequential IDs never had
it, because `[0-9]{3,}` is greedy and `REQ-0012` harvested whole and showed up
as the dangling reference it was. Fixed by requiring a non-alphanumeric
boundary after every reference, in `gr_id_run` and in the `DANGLING-REF`
harvest. `GR_ID_TAIL` was widened from the body alphabet's complement to
`[^0-9A-Za-z]` in the same fix: `i`, `l` and `o` cannot appear in a token, so
a reference carrying one is a typo and not a boundary. Pinned by four tests in
`lib.bats` and two in `check-trace.bats`.

The residue is stated under Gaps: such a reference is now ignored rather than
reported. It is not silently credited, which was the false green.

## What is deleted, and the argument for each

Four gates are removed. Removing a gate in a project about false greens needs
an argument, not a rationale.

| Deleted | Why it existed | Why it can go |
| --- | --- | --- |
| Draft ID tokens, and `finalize-ids.sh`'s whole minting half — `max_final`, the mapping scan, the rewrite pass, the `UNMINTED-DRAFT` pre-flight | assign a number that could not be known until merge | nothing is assigned at merge. The item has its real ID from the first keystroke |
| `UNANCHORED-DEF` and `UNANCHORED-DEF-UNREADABLE` | an off-column `**PR-900**:` in prose raised the mint ceiling, silently reserving a number | there is no ceiling. A definition form in prose reserves nothing at all |
| `DUPLICATE-ID` vs the base branch, with `--base` and `SKIPPED-DUPLICATE-BASE` | two branches minting the same number against one base | `merge-change` step 1 merges the base branch into the worktree **before** step 4 runs `check-ids.sh`, so every ID the base defines is in the tree the in-tree half already scans. The gate it duplicated is the one that stayed |
| `--allow-drafts` | let drafts through mid-change | a draft ID is now always a failure. The flag is `--allow-draft-files`, and it covers ledger FILENAMES only |

`--allow-drafts` and `--base` are **refused**, not ignored — a flag accepted in
silence is a check the caller believes they configured. That is what makes a
stale CI line visible at the upgrade instead of three months later.

One gate is added: `MALFORMED-ID`. The scheme change opens the hole. While
drafts existed the final ID was written by a script and was well formed by
construction; now a person types it, and `**REQ-abcdef**:` matches nothing in
the toolkit — it defines no item, no gate is keyed on it, and every check
passes over it while exiting 0.

## Mutation table

Each row reverts one production change and re-runs the whole suite. A change no
test can detect is a change with no evidence behind it. The mutations are
committed as executable scripts in
`docs/verification/2026-08-22-id-tokens.mutations/`, one `*.sh` each, so a
reviewer re-runs them rather than reconstructing them from prose. Each runs
with its working directory at the root of a copy of this tree.

**54 rows. None reddens zero tests, and none errors.** This is the fifth run;
the first four did not look like that, and what they found is the point of
running it at all:

* **Run 1 (45 rows).** `M24` and `M46` reddened **nothing** — two tests that
  could not fail. `M24` blanked the sentence in the `DRAFT-ID` failure that
  names `new-id.sh`; the test asserting that sentence had been passing on the
  `MALFORMED-ID` message all along, because its fixture wrote the draft token

  boundary from the `DANGLING-REF` harvest; that test used an ID whose
  truncation named a *defined* item, so it held either way. `M36` reddened
  nothing because no test distinguished `new-id.sh`'s pathspec from a literal.
  `M18` and `M21` errored — both written against the two-pass `MALFORMED-ID`
  implementation that the corpus run had already replaced.
* **Run 4 (53 rows).** `M13` reddened nothing once its description was
  corrected to say what it does. Deleting the `[ -r "$urandom" ]` guard changes
  the *message* and not the verdict — the draw fails anyway — and the test
  asserted only the word "entropy", which both refusal paths contain. The test
  now asserts the guard's own wording.

**Three rows are probabilistic and the table cannot say so.** `M02`, `M09` and
`M14` are caught by tests that mint 20–60 random tokens, so whether a given
property shows up is a draw: their red counts vary between runs (`M02` 1–2,
`M09` 1–3, `M14` 2–4). Every one of the three reddens at least one test in
every run observed, but a reader comparing two tables should expect the counts,
not the verdicts, to move.

## Gaps

**The method's standing limit.** The mutation set can only redden gates that
already have a test, so it cannot surface a **missing** gate. A complete table
shows the guards that exist are load-bearing; it is not evidence that the right
guards exist. The one defect found during this change — `MALFORMED-ID`
reporting nine innocent lines for one violation — was found by running the
tooling over a real 1178-file project, not by the table.

**A reference one character too long is ignored, not reported.** As a
*definition* it is caught: `**REQ-a3k9z2x**:` is `MALFORMED-ID`, because the
form is bounded by `**:` at both ends. As a *reference* — `see REQ-a3k9z2x` in
source, or an `affects:` list — it now matches nothing and no gate says a word.
That is deliberate and it is the safe direction: the alternative, and the
behaviour this branch shipped until the probe found it, was to credit
`REQ-a3k9z2`. A `MALFORMED-REF` gate would close it; it is out of scope here
and not written.

One case does stay red without extra machinery: a truncated ID in a
`verifies:` annotation leaves the item it was meant to verify with no test at
all, so `MISSING-TEST` fires on the real requirement. Pinned by "a verifies:
reference one character too long is not coverage".

**`MALFORMED-ID` cannot see a body that is valid but wrong.** A well-formed
token for an item that does not exist is a `DANGLING-REF` when referenced and
nothing at all when merely defined twice over — that is `DUPLICATE-ID`'s job.
The gate judges the shape of an ID, never its meaning.

**Markdown fences are not parsed, anywhere in the toolkit.** Stated above and
pinned by two tests. It is the same stance every other gate already took; this
change is the first to make it visible, because it is the first gate that fires
on a line with no digits in it.

**Collisions are detected, not prevented.** `new-id.sh` redraws a candidate
that occurs anywhere in this tree, tracked or untracked. It cannot see an ID
that exists only on another branch; `DUPLICATE-ID` catches that after
`merge-change` step 1. At a thousand items the birthday probability of a
cross-branch collision is under 0.1%, and the failure mode is a loud red.

**`GR_AWK_ID_RUN` freezes the body at source time.** It interpolates
`GR_ID_BODY` once, when the library is sourced, so poisoning the variable from
outside does not move it. This matters only to a test that poisons; the
constant is still built from the one definition, so it cannot drift. Recorded
in `lib.sh` at the constant.

### Carried from the independent review

These are the reviewer's notes: real, judged not worth changing here, and
recorded so the next reader does not have to rediscover them.

**`MALFORMED-ID` catches the shape it names and no other.** Three
definition-*shaped* lines are missed: `**REQ-abcdef:**` (colon inside the
bold — the realistic markdown slip), `***REQ-a3k9z2**:` (bold-italic), and
`**req-a3k9z2**:` (lower-case prefix; the pattern is case-sensitive). Each
defines nothing, is referenced by nothing, and is reported by nothing. Widening
the candidate pattern to catch them multiplies the false-positive surface the
corpus already demonstrated, so the gate stays narrow and the miss is stated.

**`MALFORMED-ID` has no suppressing flag.** `**PR-checklist**: our
pull-request checklist heading.` at column one is exit 1 with no way to allow
it. That is deliberate — the whole point is that a line looking exactly like an
item is treated as one — but it means the gate can block a merge over a
document that is not an item ledger. The remedy is always the same: indent it.

**The enumeration principle and the code disagree within twenty lines.**
`lib.sh` argues classes must be enumerated because ranges are locale-undefined,
then `GR_ID_TAIL` is `[^0-9A-Za-z]` and the legacy branch of `GR_ID_BODY` is
`[0-9][0-9][0-9]+`. Both ranges are wider than the enumeration would be, so a
locale that mis-collates them can only make the boundary and the legacy form
*more* permissive, never less — the direction is safe. The stated rule is
nonetheless not the rule the code follows everywhere.

**`GR_ID_FORCE_TOKEN` is a production hook, shipped into every project.**
`lib.sh` argues twice that an inherited environment value must never move an ID
scan, and this one moves the generator. It cannot produce an invalid ID — the
forced value goes through the same length, digit, dedup and collision checks —
and an exported value makes the second mint fail loudly rather than duplicate
silently. Kept because the collision and give-up paths are unreachable without
it, and named here rather than left to be found.

**`new-id.sh COUNT` prints incrementally.** A failure on the third of five
leaves two IDs on stdout and exits 2. Untested. The IDs printed are valid and
free, so the caller has lost nothing but the rest of the request.

**Call sites and tests no mutation covers.** `check-trace.sh`'s `ids_defined`
is a fourth `GR_SCAN_EXCLUDE` site with no pathspec-literal row, and **three**
of the 21 `new-id.bats` tests are reddened by no mutation at all — `a token
taken under one prefix is free under another` (the only guard that the
collision scan is prefix-qualified), `successive runs do not repeat
themselves`, and `mints one ID of the requested prefix`.

The third is the one worth knowing about: it *was* covered, by `M14`, and fell
off when `M14`'s red count moved — and `M14` is one of the three probabilistic
rows. So a row that draws random tokens can quietly stop covering a test
between runs without any figure changing. The count here was written as 19 of
21 on the strength of a table that had already moved; the reviewer recomputed
it from the table's own text, which is the only way to get it right.

**The "58 go red against `main`" figure is inflated.** All 21 `new-id.bats`
tests redden there for one reason: `scripts/new-id.sh` does not exist on
`main`. That is not evidence a defect was fixed. The mutation table carries the
real weight for that script, covering 18 of the 21 — the same point the derived
evidence block makes above, kept here because this is where a reader looking
for the change's weak spots will look.

**Nothing detects a stale `finalize-ids.sh` after an upgrade.** The reviewer
probed the combination: the old script runs against the new `lib.sh`, correctly
ignores token bodies when computing its ceiling, and keeps minting sequential
IDs with every gate green. Compatible rather than dangerous — but `ratchet`'s
instruction to delete it has no backstop.

**The mutation scripts need `python3` and GNU `sed -i`.** 42 of 54 use
`python3`, which the toolkit itself never depends on, and the rest use `sed -i`
with no argument, which is GNU-only. They are self-contained in the sense that
matters — each runs with its working directory at the root of a copy of the
tree, and needs no runner beyond `sh` — but not in the sense of running
anywhere the toolkit runs.

**The corpus figures cannot be checked from this repository.**
`sightings-app @ 0a7370ba` is a separate working copy on the author's machine:
the 1178-file count, the byte-identical `check-trace.sh` output, the single
`MALFORMED-ID` line and the timing triples are all reproducible only there.

**`new-id.sh` still waits on an entropy source that blocks.** The draw reads
one bounded 4 KiB block, which returns on EOF or a short read, so every source
that yields nothing *and returns* is handled and a FIFO is refused before it is
opened. A source that blocks instead — `/dev/random` on an entropy-starved host,
reached by setting `GR_ID_URANDOM` — waits in `read()` as that device is
documented to. Bounding the wait rather than the read needs a portable timeout,
which POSIX does not give and which the toolkit has no other reason to depend
on. The default `/dev/urandom` does not block on any system this targets.

**`gr_id_run` spells the boundary class twice.** The guard tests against
`GR_ID_TAIL`; the consume that follows it hand-types the complement,
`[0-9A-Za-z]+`. Nothing holds the two in step, and `M44` — which narrows
`GR_ID_TAIL` — does not exercise a mismatch. Accepted deliberately: a third
spelling of the class would be one more thing to drift, and a mismatch here
reverts to the behaviour before this change (the annotation run ends early, so
coverage is lost and the gate reddens) rather than inventing a new one. The
direction is fail-safe, which is why the drift risk is the cheaper of the two.

**`guardrails_version` is bumped to 0.2.0 in the template only.** Nothing
compares a project's configured version against the tooling it is running, so
an existing project keeps `0.1.0` and no gate notices. That is change F, still
open, and this change makes it more worth doing rather than less: the upgrade
now has a hard cliff in it.
