## What the first review round changed

An independent reviewer confirmed all eight rows of the table above by
reproduction, and found two blocking defects — both in this change, neither in
change A:

1. **The gate-input map over-rejected.** It required `doc_rmf` for `RC`, but no
   RC gate reads it. A retrofit with requirements, controls and design but no
   risk management file was refused with a message asserting a gate "could
   never run" that had just run and reported its violation — the map breaking
   the invariant stated three lines above it in its own comment.
2. **The migration table listed CRLF as an exit-2 cause** that Task 1 of this
   very change removed, contradicting a shipped test.

It also found a shape the reader cannot see that this change had *not*
rejected: a comment at column zero inside a list block ended the block,
silently dropping every entry below it. That is now handled by `cfg_list`
rather than merely reported, since the alternative was rejecting a config
people reasonably write.

## What the second review round changed

The first round's fixes were themselves unreviewed, so a second round ran. It
confirmed the corrected gate-input map by walking every gate independently, and
found **a false green created by one of those fixes**:

Making `cfg_list` skip comments so a `# …` line would not truncate a list meant
it silently **adopted** any items below into the block above. With

```
test_paths:
  - tests
# strict_paths:
  - src
```

`src` became a test path, so a `verifies:` annotation in production source
counted as a test: change A reported `MISSING-TEST REQ-001` on that tree and
change B exited 0. The shipped template's own `# coverage_command:` block has
exactly that shape.

The fix is not to pick the other reading. Both readings lose information
silently, so `cfg_list` keeps change A's semantics and `gr_check_config`
rejects the orphan outright, naming the line. An indented comment inside a
block is unambiguous and still accepted, and a YAML end-of-document marker
(`...`) — newly rejected by the first draft — is accepted again.

Three claims in this record were also wrong and are corrected above: dropping a
prefix does not switch its gates off; the artefact discriminator is behavioural
rather than the exit status; and `strict_paths`/`doc_soup` are required by no
prefix. The plan no longer prescribes the superseded `RC` rule.

## What the third review round changed

Round 3 found the closed prefix set doing what the `RC` rule had done: `DANGLING-REF`
and `DUPLICATE-ID` are keyed on the whole configured prefix list, so an extra
prefix **is** checked. With `see ADR-007` in `src/`, change A reports
`DANGLING-REF ADR-007` and exits 1; this change refused to run, told the
operator every `ADR` item "would be counted and checked by nothing", and
following that advice turned the reported violation into exit 0. The rule now
requires **at least one** gated prefix rather than that every prefix be gated —
which still closes the real hole (a config where no traceability gate runs at
all) without removing anyone's coverage.

It also found the orphan rule incomplete: a list item after a `---` or `...`
separator was orphaned but accepted, and silently dropped. Separators now break
the ownership chain like any other column-one line.

## Known gaps shipped with this change

1. **`checked:` counts items found, not items examined.** An item defined
   outside the document configured for its prefix is counted and read by no
   gate. This is change A's second gap and it stays open — the item-placement
   change closes it. The wording recording it was deliberately preserved, not
   narrowed, when the config half was closed.
2. `gr_clean` strips a trailing ` # comment` silently and quoting is not
   honoured, so any value whose own whitespace-delimited token starts with `#`
   is truncated without a diagnostic — commands and paths alike. A directory
   literally named `docs/req #1` cannot be configured. Recorded in
   `templates/config.yaml` beside the rule.
3. `check-ids.sh` and `check-signing.sh` do not call `gr_check_config`, so a
   malformed config is caught at the traceability and finalize gates only. A
   project running just `check-ids.sh` gets no config validation.
4. **This repository still has no `.guardrails/config.yaml` of its own**, so
   guardrails cannot be run against guardrails and this change cannot be
   dogfooded. `AGENTS.md` claims the project is "developed under its own
   rules"; that claim remains aspirational, and it is why the plan's
   `Implements:` line is empty rather than carrying invented IDs.
5. Change A's own gap list is unaffected by this change and remains accurate.
6. **A duplicate key, or a second list block for the same key, is accepted and
   the later one silently ignored.** Recorded in `templates/config.yaml`.
7. **Dropping a prefix from `id_prefixes` does not switch its gates off** —
   `MISSING-TEST` is keyed on `test_paths` and the rest on the document lists,
   so all of them keep firing. What it removes is that prefix from `checked:`
   and from `DANGLING-REF`'s scope, so references to it stop being checked
   while its other gates carry on. Verified: with `HAZ` removed and `doc_rmf`
   still set, `UNMITIGATED-HAZARD` still reports. Two earlier drafts of this
   entry were wrong in different ways; both were caught by review.
8. **`strict_paths` and `doc_soup` are required by no prefix**, so omitting
   either — or leaving `strict_paths:` empty — quietly narrows what
   `DANGLING-REF` scans, at exit 0. Reproduced: `implements: RC-999` in
   `src/main.c` with no `strict_paths` gives exit 0 and `sources: … strict 0`.
9. **A key written in the wrong shape for its type is accepted and read as
   absent.** `strict_paths: src` as a scalar is invisible to `cfg_list`;
   `doc_soup:` written as a `  - item` block is invisible to `cfg_get`. Both
   are pre-existing and both are squarely the class this change addresses —
   the validator checks a line's *form*, not whether the key's type matches
   how it was written. `test_paths: tests` fails closed but with the
   misleading message that the list is empty.
10. An unrecognised key is rejected even when it is a deliberate project-local
    annotation rather than a typo. The two are indistinguishable here, and the
    rejection is deliberate — but it is the one exit-2 cause that was not
    previously a gate failing to run, and `README.md` and the ratchet note now
    say so rather than over-claiming.
11. **The at-least-one-gated-prefix rule is satisfiable by `PR` alone.** `PR`'s
    only gate, `UNRESOLVED-PR`, is a warning that never sets `fail`, so
    `id_prefixes: PR` with `doc_problems` passes validation and exits 0 over a
    tree that reports four violations under the full config. Not a regression —
    change A behaves the same — and `sources:` is the tell, but the rule does
    not deliver what its name suggests in that one case.
12. **An indented `  - item` under a populated *scalar* key is accepted and read
    by nothing.** `doc_soup: …/soup.md` followed by `  - src` passes: `cfg_get`
    returns the scalar, `cfg_list` is never called for that key, the item
    vanishes. The validator checks a line's form, not whether the key's type
    matches how it was written — so an orphan under a comment or a separator is
    exit 2 while an orphan under a scalar key is exit 0. Same family as gap 9.
13. **Comment drift in `scripts/lib.sh`.** The "Every top-level key guardrails
    understands…" paragraph sits above `GR_GATED_PREFIXES` rather than above
    `GR_KNOWN_KEYS`, which now has no comment of its own. Cosmetic.
