# Random ID Tokens Implementation Plan

**Goal:** replace sequential item IDs (`REQ-014`) with randomly minted
six-character tokens (`REQ-a3k9z2`) minted at item-creation time, so parallel
worktrees and parallel GitHub PRs never contend for a number.
**Implements:** no REQ IDs — guardrails is not itself a guardrails project;
the plan and the verification record are the trace.
**Safety class:** n/a (toolkit repo). Held to the project's own standard:
every behaviour change gets a test that was watched to fail first, and every
production hunk gets a mutation row.
**Verification:** `env -u SSH_AUTH_SOCK sh tests/run-tests.sh` — all green,
plus the mutation table in the verification record.

## Why

Sequential numbering allocates against a moving base branch. Two branches
finalized against the same base mint the same number, and whoever merges
second must re-finalize. With agents working in parallel and multi-person
GitHub collaboration that is churn at best and a merge-time rewrite of every
`verifies:` annotation at worst. A token minted once, at item creation, is
allocated by nobody and collides with nobody.

Decided by the user on 2026-08-20 with two constraints:

* every token carries **at least one digit** — otherwise `REQ-[a-z]{6}`
  matches ordinary hyphenated English (`REQ-argued`, `PR-update`), turning
  prose into dangling references;
* the alphabet **excludes the ambiguous characters** `0`/`o` and `1`/`l`/`i`.

## The token

Alphabet: `23456789abcdefghjkmnpqrstuvwxyz` — 31 symbols, lowercase only.
Length 6, at least one digit: 31⁶ − 23⁶ = 739 467 792 tokens.

The token is **minted once and never recomputed**. It is deliberately NOT a
content hash: a hash changes when the item text is edited, which would break
every `verifies:`/`traces:` reference pointing at it.

Collisions are not prevented, they are detected. `new-id.sh` rejects a token
already present anywhere in the tree; `DUPLICATE-ID` in `check-ids.sh` catches
a cross-branch collision once `merge-change` step 1 has merged the base branch
into the worktree. At 1 000 items the birthday probability of a cross-branch
collision is under 0.1%, and the failure mode is a loud red, not a wrong ID.

## Migration

Both forms are accepted, everywhere, permanently — `(<token>|[0-9]{3,})`.
Existing projects keep their sequential IDs; only new items get tokens. There
is no flag day and no rewrite of an existing SRS.

## What is deleted, and why it is safe

| Deleted | Why it existed | Why it can go |
|---|---|---|
| `finalize-ids.sh`'s minting half (`max_final`, the mapping scan, the rewrite pass, the `UNMINTED-DRAFT` pre-flight) | assign a number that could not be known until merge | nothing is assigned at merge any more |
| Draft ID tokens `<PREFIX>-DRAFT-<branch>-<n>` | hold a place until a number was assigned | the real ID exists from the first keystroke |
| `check-ids.sh` `UNANCHORED-DEF` / `UNANCHORED-DEF-UNREADABLE` | an off-column `**PR-900**:` in prose raised the mint ceiling, reserving a number silently | there is no ceiling. A token in prose reserves nothing |
| `check-ids.sh` `DUPLICATE-ID` vs base, `--base`, `SKIPPED-DUPLICATE-BASE` | two branches minting the same number against one base | the in-tree half subsumes it: `merge-change` step 1 merges the base into the worktree *before* step 4 runs `check-ids.sh`, so any ID the base defines is in the tree the in-tree half scans |

Each deletion removes a gate. Every one is recorded in the verification record
with the argument above, and each gets a mutation row proving what the
remaining gates still catch.

## What is added

`MALFORMED-ID` in `check-ids.sh`. The scheme change opens a hole the old one
did not have: under drafts, the final ID was produced by a script and was
always well formed. Now a human or an agent types it, and `**REQ-abcdef**:`
— six letters, no digit — matches no pattern in the toolkit. It defines
nothing, it is referenced by nothing, and every gate passes over it in
silence. That is the exact false green this project exists to remove, so a
definition-shaped line whose body is not a valid ID is now a violation.

It fires on legacy short IDs too (`**REQ-01**:`), which the old `[0-9]{3,}`
form also passed over in silence. That is a real pre-existing defect in any
project that has one, and `ratchet`'s upgrade section says so.

* validate `COUNT` is a positive integer;
* entropy from `${GR_ID_URANDOM:-/dev/urandom}`; **die** if it is unreadable
  rather than falling back to `$$`/`date`, which is a predictable ID
  generator wearing a random one's clothes;
* draw with `LC_ALL=C tr -dc "$ALPHABET" < "$src" | dd bs=1 count=6` — `tr -dc`
  is rejection sampling, so it is unbiased; `dd`, not `head -c`, because
  `head -c` is not in POSIX head (the same reason `gr_check_config` detects the

  (`git grep -qF --untracked -- "$id" -- . "$GR_SCAN_EXCLUDE"`), or was minted
  earlier in this same run;
* give up after 100 attempts per ID with exit 2 and "could not mint" — an
  infinite loop here would hang a merge;
* `GR_ID_FORCE_TOKEN`, when set, replaces the draw so the collision and
  give-up paths are testable. Documented in the script as test-only.

## Task 5 — `finalize-ids.sh` → `finalize-docs.sh`

The ledger-filename dance is about files, not IDs, and stays: a change writes
`docs/<area>/DRAFT-<branch>-<slug>.md` so parallel worktrees never touch one
file, and the merge date can only be known at merge.

`git mv scripts/finalize-ids.sh scripts/finalize-docs.sh`, then delete
`max_final`, the mapping loop, the `UNMINTED-DRAFT` pre-flight and the rewrite
pass. What remains is the config/doc validation, the rename planning with its
whitespace rejection and collision suffixing, `--dry-run`, and the rename
loop. `--base` goes with the minting. `tests/finalize-ids.bats` becomes
`tests/finalize-docs.bats`; every minting test is deleted and listed by name
in the record, every rename test stays.

Renaming the script is deliberate. `finalize-ids.sh` that finalizes no IDs is
the kind of name that outlives what it describes and misleads the next reader.
`ratchet`'s upgrade note tells operators to delete the old file.
